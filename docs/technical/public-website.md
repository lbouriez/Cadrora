# Public photographer website

## Scope

Cadrora is both an event-gallery application and the photographer's public website. The two surfaces share the React build and visual system, but they have different availability and authorization characteristics:

- `/` presents the photographer and services, plus recent public galleries when the owner enables gallery discovery;
- `/services` presents the owner-enabled portrait, family, wedding, brand, corporate, and childhood offerings as image-led cards;
- `/portfolio` presents permanent owner-managed collection cards; `/portfolio/:slug` opens a collection's photos, independently of customer galleries;
- `/galleries` dynamically lists published public and protected galleries enabled for public listing, newest by event date first, while gallery discovery is enabled; showcase journeys belong on `/` and no legacy `/events` alias is registered;
- `/contact` publishes direct contact coordinates without a form, plus a click-to-load OpenStreetMap card (or optional Google Maps card);
- `/privacy` explains gallery and face-search privacy;
- `/e/*` is the event-gallery surface and may require an event grant;
- `/admin/*` is always authenticated and Worker-guarded.

The website shell must remain useful when the event API is unavailable. A gallery-list failure therefore renders a quiet status message and does not replace the landing page with an error screen.

The shared Contact page uses the site logo for the Home return path and has no duplicate back button. Its content area grows to keep the footer at the bottom of a short viewport without reserving a second full viewport or leaving excess space after the last content block.

The shared public masthead stacks the optional construction notice and navigation in normal flow on interior pages, and overlays that same stack on the immersive Home photo. This keeps the brand and menu at the same coordinates on every route, even when the notice wraps on a narrow screen. Services, Portfolio, Galleries, Privacy, and Contact use one editorial introduction component and shared top spacing; immersive Home and About keep their distinct photo layouts.

Home and Services cards place their localized service title over the photo with a theme-aware contrast gradient; the description stays below the photo. The Portfolio collection editor places its metadata, photo upload, and photo list in full-width rows so new collections do not leave an empty grid column. The Recent stories controls are disabled while the public gallery directory is hidden; their saved values are retained if the directory is enabled again.

The shared public menu calls Services **Sessions** / **Séances**. The shared header has no top margin or sticky top offset, so its position does not shift between Atelier's Home and interior pages. Atelier Giulia's build-time profile selects a vertical Home session presentation and menu order, while Cadrora keeps its card presentation. Each Atelier session panel fills the initial viewport, including the area behind the shared transparent header. On desktop, the shared links, appearance, and language controls sit over the photo; at mobile widths, the brand and menu button remain over the photo and the same navigation opens as a full-viewport panel using semantic theme colors, with appearance and language controls inside it. Interior pages retain the ivory header. Panels use the existing enabled, Home-eligible services in admin order, respect the Home services limit, and use their own published photos and bilingual copy. The full-height panels are in normal page flow: each wheel, trackpad, keyboard, or finger gesture reveals one session from below and settles it fully before another gesture advances, with one final step to the footer. Shared enter-on-view motion reveals the text, while reduced-motion preferences show it without transition. There is no automatic advance or carousel control. Atelier's palette is supplied through semantic theme tokens; the menu, i18n, and routing remain shared. See [ADR-039](../decisions/ADR-039-profile-session-slides-and-about.md).

The shared `/about` page has an owner-controlled visibility switch, bilingual text, and a prepared portrait managed in the **About** admin tab. Its text editor and photo pipeline reuse the existing localized fields and marketing upload. A disabled page disappears from the menu and redirects to Home; its uploaded photo is no longer served. Atelier Giulia uses an immersive photo presentation, while Cadrora uses its standard editorial design. When there is no owner photo or D1 is unavailable, each profile uses compiled fallback content and a static example image.

Service cards may show a bilingual price range and open a shared details dialog with duration, explanation, included items, and a contact action. The existing admin service form edits these fields for both new and existing services. Unedited built-in services show clearly labelled sample prices and durations until the owner saves their own copy; the dialog says that the actual offer is confirmed before booking. The admin Portfolio tab creates collections with bilingual title and description, service, order, cover, and publication controls. Each collection accepts multiple photos with bilingual alt text and order. The screen reuses the browser service-image encoder to create preview, small, medium, and large variants; these are display copies, never original downloads. The public index shares the gallery card family, and collection pages reuse the gallery photo mosaic, viewer, and `ProgressivePhoto` loader without customer-only controls. The public shell and service text remain usable if the portfolio API is unavailable.

The admin Website setting can hide Galleries from navigation once every listed public gallery is changed to Unlisted, taken offline, or changed to password-protected access. Unlisted public galleries stay accessible without a password by direct link and do not block the setting. Public drafts and offline galleries do not block it either; they may only be republished as Unlisted while it stays hidden. The Home recent-gallery and showcase sections, public gallery directory API, and `/galleries` page stop promoting galleries; the portfolio remains visible. Direct `/e/*` customer links retain their existing availability and password rules. New galleries start protected. The admin always shows a copyable direct URL for each gallery, including drafts and offline galleries; a copied link only works when the gallery is available. This switch does not delete media or revoke a protected-gallery grant.

The Worker serves `/robots.txt` as text and `/sitemap.xml` as XML on every site profile. The sitemap contains marketing pages, including `/portfolio` and published `/portfolio/:slug` collections; `/galleries` and every `/e/*` customer gallery URL are omitted regardless of status. Both paths stay in `assets.run_worker_first` so the SPA fallback cannot replace them with HTML. The customer gallery directory and pages use `noindex,nofollow`; public gallery direct links still provide social preview metadata. A D1 outage leaves the static marketing sitemap available without collection URLs.

The Worker also serves `/llms.txt` as Markdown before the SPA fallback. Its title, summary and language come from Worker vars populated from the selected site profile by the deployment scripts; Wrangler bundles the Worker separately from Vite, so Vite's client-side defines must not be used in server routes. Links use the request hostname and point only to marketing pages and the sitemap. The guide works even when D1 is unavailable. Keep `/llms.txt` in `assets.run_worker_first` so a missing file can never return the application HTML with HTTP 200.

## Public profile configuration

Build-time presentation profiles live under `sites/<id>/site.ts` and are selected by `CADRORA_SITE`. The default `cadrora` profile retains the product showcase; `atelier-giulia` reuses the same pages/components with its own brand, section order, bilingual copy and semantic theme tokens. Put shared layout and interaction improvements in `src/app` so both sites inherit them. Use `pages` in a site definition only for a genuinely distinct marketing page; gallery, contact settings, privacy behavior, and admin remain shared. Profiles must not contain credentials or invented real-world contact coordinates. The Cadrora showcase can include a `featuredSites` Home section whose cards are compiled from `home.featuredSites`; each card supplies an external URL, name, optional local logo and FR/EN description resource key. Adding another site needs an approved public link and bilingual copy, with no Worker request or client upload. See [ADR-013](../decisions/ADR-013-site-profiles.md) and the [Atelier Giulia deployment runbook](../deployment.md#atelier-giulia-from-this-repository).

Profile branding is built into the static shell: `site.ts` provides `logoUrl` for the shared header and `profile.json` provides `document.icon` for the favicon. PNG icons also provide the Apple touch icon. The default Home hero image is set in both `site.ts` and `profile.json`; the latter supplies the Worker fallback when no admin image override exists. The neutral `studio` profile has no header logo and uses a small SVG favicon; replace these with licensed branding before launch. Atelier Giulia uses a transparent camera mark for the header (`atelier-giulia-logo.png`) and a matching ivory-backed PNG icon (`atelier-giulia-icon.png`). See the [owner launch checklist](../after-deployment.md).

`npm run build` rejects any image in `public/brand/` above 350 kB. Export large opaque or photographic brand assets as WebP/AVIF before adding them to a profile; retain PNG where transparency or browser icons require it. This limit applies to all profiles so a future large asset does not silently reach mobile visitors. The shared gallery `ProgressivePhoto` still handles D1/R2 photo variants independently. The first visible gallery cover and first photo in each initial gallery column start eagerly; further photos remain lazy.
The shared private-gallery cover is a 1200 px WebP suited to directory cards, and the Atelier browser icon is a compact 256 px PNG; originals remain recoverable from Git history.
The build verifies the dimensions in `src/shared/brand-photo-dimensions.json` and generates 320/640/960/1280 px WebP copies under ignored `public/brand/responsive/` without upscaling. Shared `BrandPhoto` and `ProgressivePhoto` render a small preview followed by one browser-selected display copy using `sizes` and `srcset`; gallery cards, tiles, and the viewer no longer fetch an unconditional intermediate copy. Add a new brand photo to the dimensions file when it should use this path. Unsupported profile image URLs retain the normal image fallback.
The first marketing image, first directory card, and first gallery tile set high fetch priority on both preview and chosen display copy. Other images retain normal priority so the page does not promote an entire photo grid over scripts and styles.
The public router loads gallery browsing and face search code on those routes; shared translation resources remain available to links on other pages. Production builds publish client source maps for debugging. Shared Zod schemas import the configured `src/shared/zod.ts` entry so CSP-safe jitless validation is active before any schema is constructed.

Client-side page links reset window scroll to the top, including links to the current page. Hash links and query-only changes retain their scroll behavior, and opening or closing a photo viewer in the same gallery preserves the gallery's scroll position.

Dark presentation panels use the semantic inverse text colour for body text and eyebrows, including the approach and contact sections. Gallery card links derive their accessible name from their visible date, title, and description.

Public contact content has compiled `VITE_*` fallbacks and owner-editable D1 overrides. These values are public by design and must never contain secrets. D1 absence or API failure never blanks the public site.

The canonical reader is `src/app/public/siteProfile.ts`. Do not access public build variables throughout components or duplicate the profile in translations. Site-specific copy overrides are merged into the shared FR/EN resources at initialization, not hardcoded in a page. ## Runtime site settings

The owner can enable a short FR/EN **site in progress** notice under **Website**. It appears above the shared public header and can be disabled from the same checkbox. The setting lives in D1 and comes from the existing `/api/v1/site` response with name, description, theme, and other public settings. It starts on for Atelier Giulia when that instance's initial settings run, and off for other site profiles; later owner choices always win. A failed settings read leaves the static public pages usable without a notice. No R2 read or separate notice request is involved. See [ADR-037](../decisions/ADR-037-public-site-progress-notice.md).

The owner can edit the French and English site descriptions under **Website** and the short line after the site name under the final **Footer** section. These live in `site_settings.site_copy` as validated bilingual JSON, with the compiled profile as fallback when D1 is absent. The owner-editable `site_name` remains available to other shared components. The Home section also has a collapsed introduction editor for bilingual text, an ordered list of up to six buttons with translated labels, approved destinations and primary/secondary theme styles, an optional photo tag, and a browser-prepared photo. One reset restores the compiled example text, buttons and image. The separate Services/Galleries page introductions remain code/profile-owned. The public browser title and description update after the settings request resolves, and `/llms.txt` reads the same D1 values. Initial static HTML metadata, social link previews and crawlers without JavaScript still use `profile.json` until the next build. Edit the profile as well when those must change. See [ADR-027](../decisions/ADR-027-owner-editable-brand-copy.md), [ADR-029](../decisions/ADR-029-owner-managed-home-introduction.md), and [ADR-030](../decisions/ADR-030-configurable-home-actions.md).

The shared footer places a small bilingual “by Cadrora” credit, local Cadrora logo, and link to `https://cadrora.com/` immediately after the copyright and tagline on the same row when space allows. Its vertical spacing is compact across site profiles. The Cadrora showcase retains its demo notice instead. The credit does not depend on the site-settings API.

The Cadrora showcase, neutral standalone `studio`, and Atelier Giulia have separate compiled name/description defaults. New isolated instances select `studio` unless `CADRORA_SITE` is set. Studio starts with no header logo and an SVG favicon; replace its provisional sample imagery and icon with licensed branding before launch. PNG icons also provide the Apple touch icon. The existing Atelier Giulia footer and descriptions are seeded into D1 only when `site_copy` is empty, so later owner edits win.

An authenticated owner can set site name, new-visitor language, visitor appearance, and a GA4 Measurement ID under **Website** at `/admin/settings`. Theme policies are `light`, `dark`, `both`, or `system`. `both` displays a Light / Dark switch and preserves a visitor’s local choice; a fixed policy removes the switch; `system` follows live `prefers-color-scheme` changes. Under **Home**, the **Recent stories** settings let the owner hide the home gallery section or show 1–12 public galleries (6 by default), newest event dates first; `/galleries` remains complete and includes listed protected galleries. The separate Home services limit shows the first 1–12 eligible services in admin order, default 3. Under **Services**, the owner edits bilingual service copy, short Home descriptions, photos, ordering, Services-page visibility, and Home eligibility; custom services require a prepared photo before publication. Each built-in service has **Restore example**, which restores its compiled text and photo together without changing its order or visibility. Custom services have no compiled example. Under **Contact**, the owner edits email, phone, studio location, service-area description, and a complete optional latitude/longitude/radius tuple. These are D1-backed runtime settings, not Vite variables, so they can change without rebuilding public content. The public shell treats the reads as optional and falls back to compiled profile values if `/api/v1/site` or `/api/v1/services` is unavailable. Public responses are cached for 60 seconds; existing open pages may need a refresh.

The Contact editor distinguishes the studio location from the visitor-facing area served. An optional city autocomplete fills only the map centre coordinates; the owner still sets a radius and explicitly saves. It calls Photon's public demo endpoint from the admin browser after three characters with a short debounce, at most five place results and abort on changed input. It sends no visitor data and does not run on public pages. The response is schema-validated. The provider may throttle or become unavailable; manual coordinates are the fallback. Keep its hostname aligned in the static and Worker CSP `connect-src` rules. [Photon's own usage note](https://github.com/komoot/photon#demo-server) permits reasonable project use but gives no availability guarantee; a high-volume operator should use a supported provider or their own instance rather than relying on the demo endpoint.

The admin Site settings page presents Website, Usage & limits, Home, Services, Contact, and Footer as separate anchored sections in one form. Description, footer, and Home introduction use the reusable localized field: one input in the admin language, a translation dialog generated from supported languages, and a missing count for enabled languages. The introduction saves independently from the other site settings; the other site settings still use their main Save button. Keeping every section mounted preserves unsaved edits while an owner moves between them. The section navigation is touch-sized and sticky. The Services editor previews each card's effective photo using the public card component: the uploaded image when present, otherwise the compiled default for a built-in service. Galeries and Portfolio have their own admin pages at `/admin/galleries` and `/admin/portfolio`; `/admin` forwards to Galeries. Both pages show existing work before the creation form. The Galeries page has one optional service category selector on both creation and editing. Both photo workspaces reuse the cover picker and dropzone; new portfolio uploads have a 2560 px maximum large variant and no original/download variant. A gallery's reversible availability control appears before its permanent deletion control, including on narrow screens. The read-only demo keeps controls interactive but disables final writes.

The public shell starts in the static light appearance while its optional D1 settings read is pending, without a provisional theme switch. Once settings resolve, `useTheme` applies the configured policy before paint; an unavailable API falls back to the visitor-selectable theme. This prevents a saved dark preference from briefly overriding a fixed light studio theme. Gallery forms accept only a calendar date; the stored ISO instant is local noon in the owner's timezone so a midnight daylight-saving transition cannot change the intended date. Gallery cards/listing copy shows the date without an hour.

The GA4 ID must match `G-[A-Z0-9]{6,20}` or be null. With no ID, no Google tag loads. With a valid ID, only explicit analytics consent on the marketing-route allowlist loads `gtag.js`. The `dataLayer` command queue uses the `arguments` object expected by Google's tag, and consent remains granted across marketing-page navigation; leaving the allowlist or withdrawing consent disables collection. Changing the ID uses the new runtime value, never arbitrary owner-provided script code. Gallery/admin/media/face-search paths remain unmeasured. The consent banner remains available through the footer.

Both `public/_headers` (static pages) and `src/server/middleware/securityHeaders.ts` (Worker routes) must retain the same consented GA4, no-Ads CSP destinations: the Google tag script host plus the Google Analytics beacon/image hosts. The browser test uses a fake D1 Measurement ID and intercepts the script request to prove consent and page-view wiring; it cannot prove that Google received a hit. After configuring a real GA4 property, verify a consented marketing page sends a `page_view` request to `/g/collect` with a successful response, check Google's Tag Assistant and Analytics DebugView, and verify that gallery/admin routes stay unmeasured. Loading `gtag.js` alone is insufficient evidence of collection. Do not enable advertising destinations without revisiting the privacy decision and CSP.

Public HTML sends `Cache-Control: no-transform` to prevent Cloudflare Web Analytics from injecting its separate RUM beacon around the consent gate. Keep this directive on both static marketing routes and Worker-served gallery HTML; do not allow the beacon in CSP as a substitute. The Cloudflare account's Web Analytics automatic setup can also be disabled in its own settings.

The owner supplies the approximate travel centre and radius under **Contact**. The Cadrora showcase seeds Montréal and 125 km into this same D1 setting only if it is still at its initial, untouched value; subsequent owner edits or clearing the map are never overwritten. There is no hard-coded display radius in the Contact component. If the tuple is absent, the map card is hidden, while the rest of Contact remains useful. Without `VITE_GOOGLE_MAPS_EMBED_KEY`, a visitor can press **Display the map** on the local, region-neutral illustrated preview to load an OpenStreetMap iframe; no key or Google Cloud account is required. The preview asset `public/brand/service-area-preview.webp` is project-owned, contains no real map or location labels, and can be reused unchanged by other installations. It fills the full map column before the click. The map and its tiles are fetched only after that click. The OpenStreetMap vector layer fits a bounding box centred on the configured coordinates with 10% margin beyond the configured radius, avoiding the raster layer's whole-step zoom rounding. The iframe provides OpenStreetMap attribution, also linked in the card once it is shown. The Google Maps outbound link is optional for visitors. The radius frames an approximate map view and is stated in text; it is not a polygon or exact travel guarantee. The community-hosted OpenStreetMap tile servers are best-effort and have a [usage policy](https://operations.osmfoundation.org/policies/tiles/); a high-traffic deployment should use a suitable tile provider or its own infrastructure. No bulk tile prefetching is permitted.

If the operator supplies a restricted `VITE_GOOGLE_MAPS_EMBED_KEY`, the click-to-load iframe uses the official Google Maps Embed API instead. Google requires a Cloud project with billing enabled even though the Maps Embed API currently lists no usage charge. See [Google's Embed API quickstart](https://developers.google.com/maps/documentation/embed/quickstart) and [key restrictions](https://developers.google.com/maps/api-security-best-practices).

## Design and content rules

- Keep all user-facing copy in both FR and EN resources.
- On a photographer's own site, address visitors as the studio using "we/you" ("nous/vous") or neutral wording. Do not refer to "the photographer" in the third person in visitor-facing gallery, contact, or privacy copy. Product-demo and owner-login copy may describe the application, but should not make a real studio sound like an external party.
- Write for visitors and photographers who do not know the implementation: describe what they can do and what happens to their photos, not Workers, databases, vectors, variants, or deployment details. Keep necessary settings such as a Google Analytics ID specific enough to act on. Preserve accurate consent, gallery-scope, cost-limit, and deletion disclosures in plain language.
- The privacy overview uses a demo-specific paragraph only when the showcase gate is enabled; other installations must not claim their people or contact details are fictional.
- Reuse the semantic tokens and shared button primitives.
- Do not load remote fonts, forms, or stock images. GA4 is consent-gated and marketing-route-limited. The contact map is click-to-load only; Google Maps is optional, OpenStreetMap is the keyless default.
- The landing and contact HTML routes remain static assets. The landing page may read optional D1 site settings, service cards, and public galleries in the browser; contact may read optional site settings.
- A protected or unlisted event is never promoted by the public landing-page query.
- Treat the supplied logo at `public/brand/cadrora-logo.png` as the canonical brand asset.

## Public experience system

The public shell is deliberately touch-first: controls meet the shared `--control-min-size` target, the header is a compact frosted surface, and the language action uses the shared `IconButton` primitive rather than a page-specific control. Its visible FR/EN label matches the navigation typography and has no decorative circle; the button's transparent 44 px hit target remains. The header theme action shares the same target size. `tokens.css` owns colour, spacing, elevation, and motion values; `components.css` owns button and icon-button interaction states. Do not add an isolated colour, radius, or animation to a public page when a semantic token or shared primitive can express it.

Below the tablet breakpoint, the shared header collapses navigation into an accessible menu on the same row as the brand and appearance controls. The landing-page CTAs use shorter FR/EN visual labels at narrow widths while retaining their full accessible names. Keep the hero photo selector scoped to the direct child image: descendant selectors also resize the small face-search portrait overlay. Service and gallery card images must preserve visible faces at both phone and laptop widths; a full-photo fit is preferable to cropping a face.

Return navigation on the gallery, face-search, and contact pages uses the shared `BackLink` component and its one `.back-link` theme rule. Generic public text-link styling applies only to unclassed anchors, so it cannot silently change a component link's colour or border.

The face-search entry presents consent and camera/file choices together. The two fictional test portraits are illustrated download cards so visitors can recognize the demo subjects before selecting a file. The shared privacy notice uses the runtime site name and the site's Contact page, and describes actual gallery access, shared choices, optional face search, analytics consent, map loading, and asynchronous deletion in FR and EN. It does not supply a legal company identity or privacy officer that the site has not configured; operators must publish their required local contact details. Storage and authorization details stay in the technical documentation.

`public.css` defines the public card family used by the landing page and `/galleries`: compact demo journeys, image-led service cards, and image-led live-gallery cards. The gallery card renderer is shared in `PublicEventCards.tsx`, so a CTA is always a themed button rather than an underlined text link. The optional AI journey is the primary demo action and must point to `/e/find-your-photos/find`; demo credentials belong only on the protected-gallery unlock or demo-login screen where they are needed, never in a promotional card.

The shared gallery directory uses stable `auto-fill` card tracks so a single gallery retains the same card width as a larger collection; a narrow phone may still use the full available width. Locked cards use the profile's generic private-cover image, not a protected photo or a public R2 object. Keep the subtle blur and lock treatment without degrading the source asset itself.

The consent panel keeps a stable, scrollable height while optional D1 analytics settings resolve, so its bottom-anchored box does not jump when the second action appears. Gallery pages reserve one viewport of main content and use the same wide layout during the initial event read, keeping the footer below the fold while the photo list arrives.
The public main region reserves one viewport on marketing pages with dynamic cards so those cards cannot shift a visible footer. Contact instead lets its content set the page height and keeps its footer at the bottom when the content is short. It keeps locally compiled coordinates visible while D1 loads and reveals the service-area map and expectations only after the optional settings request settles; the fallback content still appears if D1 fails.

Motion includes press feedback, small elevation changes, image zooms, and shared `MotionReveal` section/card entrances using semantic tokens. The hero image, demo cards, services, and public gallery cards use the same reveal component. Respect `prefers-reduced-motion`: a browser requesting reduced motion sees the static presentation, with no entrance or hover transform; no transition is required to understand or operate the site, and browsers without IntersectionObserver show all content immediately. The fictional triptych, AI gallery cover, and brand/corporate/children photos in `public/brand/` are project-owned generated demonstration media: they may be replaced by an operator's licensed imagery, but must not imply that fictional people are clients. Gallery-card image crops use an upper focal point to preserve faces.

Text placed on photos uses the shared `--color-on-photo` and overlay tokens; never derive its foreground from `--color-background`, which becomes dark in dark mode and loses contrast against the photo overlay.

## Validation

After changing the public site, run `npm run check`, `npm run test`, `npm run build`, and the relevant Playwright tests. Inspect `/`, `/services`, `/portfolio`, `/galleries` when enabled, `/contact`, `/privacy`, the public gallery and finder, and the demo admin login at 320–390-pixel phone widths and a desktop viewport, in FR and EN. Verify the menu, consent panel, image focal points, and no horizontal overflow; check contact values both configured and empty.
