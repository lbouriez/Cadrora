# ADR-032: Permanent portfolio, service details, and gallery directory control

Status: accepted by the owner's 2026-09-27 request. Extends ADR-012 and ADR-028.

## Context

The public gallery directory was carrying the photographer's marketing work even though customer galleries can expire, be unlisted, or require a password. Services had no structured duration or price information. The owner needs a permanent, categorized portfolio and a way to remove the gallery directory from the public website while retaining direct customer links.

## Decision

- New galleries start password protected. Public galleries remain an explicit option only while the global gallery directory is enabled. The admin publication panel always shows the direct URL and a copy control, including for drafts and offline galleries; those links become usable only when availability permits and never replace the gallery's normal access check.
- The owner can disable the gallery directory after changing listed public galleries to Unlisted, taking them offline, or changing them to protected access. Unlisted public galleries keep working without a password by direct link and do not block the setting; neither do public drafts or offline galleries. The D1 constraint and Worker reject new public galleries and republication into the directory while disabled. The public header, Home recent galleries and showcase journeys, and gallery index API omit gallery discovery. `/galleries` redirects to `/portfolio`; direct `/e/*` links retain their normal availability and access rules. This clarifies the owner's 2026-09-27 unlisted-gallery requirement.
- Customer galleries and the `/galleries` directory are never included in `/sitemap.xml` or `/llms.txt`, regardless of the directory setting or gallery status. Gallery pages and the directory send `noindex,nofollow` to crawlers; public gallery share previews remain available by direct link. The portfolio stays in the sitemap.
- `/portfolio` is a static public page shell with one section per enabled service. Portfolio photos are uploaded separately from customer galleries, so gallery withdrawal cannot remove marketing images. Each photo has a service, bilingual alt text, an order, and four browser-prepared variants generated by the shared service-image encoder. The public page uses `ProgressivePhoto` for lazy preview and browser-selected responsive sources. D1 publishes a photo only after all four variant rows and corresponding R2 objects are verified. Public media requests check the published D1 row and current service visibility. Deletion removes the D1 publication first and queues retryable cleanup of D1-derived R2 keys.
- Service copy gains optional bilingual duration, price range, and longer details, editable in the existing admin create/update form. The Services page displays the price range on its card and opens the complete details in a shared accessible modal. The admin Home introduction can target `/portfolio`.

## Consequences

No new dependency or customer-gallery media access is introduced. Portfolio images count toward the existing storage quota. Public HTML stays static and useful if D1 is unavailable; live portfolio media depends on D1 and private R2. Existing service records remain valid without the optional detail fields. The gallery directory switch is a discovery preference, not an access or deletion mechanism.
