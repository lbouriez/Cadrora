# Admin guide

New to Cadrora? Start with the [project overview](../README.md). For the full account setup, see the [deployment guide](deployment.md); before changing usage limits, review the [free-tier and cost examples](free-tier.md).

Cadrora has one photographer-admin authority. It is not a multi-user or multi-photographer product. Admin API and page protection are enforced by the Worker on every hostname, including previews and `workers.dev`.

## Sign-in modes

Set `ADMIN_AUTH_MODE` to exactly one of:

- `password`: requires the matching encrypted `ADMIN_SECRET_HASH` and `AUTH_PEPPER` generated by `npm run setup:admin-credentials`, as described in [`technical/authentication.md`](technical/authentication.md). Successful login creates an opaque, D1-backed session. The cookie is `__Host-cadrora-admin`, `HttpOnly`, `Secure`, `SameSite=Strict`, and scoped to `Path=/`.
- `cloudflare-access`: requires `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`. The Worker verifies the `Cf-Access-Jwt-Assertion` signature, issuer, audience, and expiry itself. Edge Access policy is defense in depth, not a substitute for Worker verification.

Login and protected-gallery unlock require server-side Turnstile verification. Five failed password attempts from one `CF-Connecting-IP` block the next attempt for 15 minutes. Every state-changing `/api/v1/admin/*` request checks that `Origin` exactly matches the request origin.

Logout revokes a password session in D1 and clears its cookie. A password session is also rotated when `GET /api/v1/admin/session` succeeds. Expired or revoked rows no longer authenticate.

The official Cadrora showcase also exposes a clearly labelled **demo** sign-in when the deployment explicitly sets `CADRORA_SEED_DEMO=true`; the default is off. Its published credentials create a separate one-hour, stateless `read-only` session; they are intentionally not a secret and are not an operator credential. The Worker—not the disabled UI—allows only session, event-list, publication-readiness, usage, and site-settings reads. Every mutation and every unrecognized admin read returns `DEMO_READ_ONLY` before D1 or R2 is touched. The reserved `demo-private` gallery password has a similarly narrow showcase-only bypass; all real protected events use HMAC verification with the secret pepper. Do not reuse demonstration credentials or enable the showcase gate for an operator deployment.

## Admin UI

The SPA lazily mounts Worker-guarded admin routes at `/admin/login`, `/admin`, `/admin/settings`, and `/admin/galleries/:eventId/import`. Every browser and API path uses **gallery**; the `eventId` parameter name is only an internal identifier. The login route renders the Turnstile challenge; it does not expose a Turnstile secret. The dashboard lists galleries and, for an owner, starts with **New gallery**. Create the gallery there, then open **Settings** on its row to change access, retention, downloads, face search, optional nearby-moment suggestions, viewer metadata, and originals. Nearby suggestions can be enabled only while face search is enabled; they add at most four photos before and four after each direct match when their real capture timestamps fall within five minutes. The viewer-metadata choice is per gallery, defaults off, and reveals only filename, capture date/time (including seconds and timezone), and dimensions. **Import photos** opens the browser import and publication workspace.

**Site settings** controls the public languages, default language, and colour policy. The language menu accepts one or both currently translated languages. The default must be one of those choices. With one language, the public language button is hidden and every visitor receives it; with both, visitors can switch and their choice is remembered locally. For colour, choose fixed light or dark, follow each visitor's system setting, or let visitors choose. Visitor choice shows the Light / Dark switch in the public header; fixed and system policies remove it. These settings live in D1 and are not build variables, so language and theme controls are intentionally absent from the admin header.

The same screen exposes owner-controlled free-tier guardrails for gallery count, stored media, and indexed faces. Gallery count means separate galleries, not photos: the checked-in deployment allows 50 galleries and up to 2,000 photos in each gallery. Each owner value may be lowered but cannot exceed the deployment ceiling. The usage summary comes from D1 records and enforcement occurs in the corresponding server write path. Lowering a limit below current usage retains existing galleries, media, and vectors while preventing new writes. These per-instance settings do not measure account-wide Cloudflare traffic or other deployments; use the Cloudflare dashboard for those pooled quotas.

The showcase demo deliberately displays the same workflow—including Create gallery, gallery settings, Site settings, Import photos, and Publish gallery—so it is possible to understand the product. Form controls remain interactive locally, but their final save/create/publish controls are disabled. Its Worker session remains read-only: it permits only the explicitly documented reads and rejects every update, upload, or publish request even if a visitor changes the browser UI.

The browser UI is still not a substitute for validating deployed authorization. Test the exact protected hostname and API response before relying on it operationally. Do not weaken `/admin` protection or expose a password/token in browser configuration.

## Gallery lifecycle

The live admin API can create, list, and update galleries. A gallery has a stable slug, one of `draft`, `published`, or `unlisted` visibility states, and either `public` or `protected` access. The internal D1 table is still named `events`, but that storage name never appears in an HTTP path or interface label.

- Draft galleries return 404 to public routes.
- Published public galleries are listed by the landing-page query.
- Unlisted galleries are available by direct URL but are not listed or promoted.
- A protected gallery needs a password. Updating it increments the access version and invalidates existing gallery grants.
- In a protected gallery, visitors with the password can tap the heart on a photo in the gallery or viewer. There is one shared heart per photo: everyone with access sees the current choice after refreshing, and anyone with access can remove it. Public galleries have no hearts, and no visitor-specific favorites or counts are kept.
- Setting access to public removes its stored gallery credential.

Create a gallery before declaring an import. Creation accepts title, optional slug/description, start time, timezone, visibility, access, downloads, face-search choice, viewer-metadata choice, and an optional retention period. The **Offer original files** choice appears only after downloads are enabled. Leave retention empty to select **unlimited** retention; this stores `NULL` rather than a hidden default expiry. The server creates a slug from the title if no valid slug is supplied; it resolves collisions by adding a suffix.

After importing, open **Settings → Gallery cover** to choose one of that gallery's ready photos. The selected photo appears on its public card once published. Draft and password-protected galleries remain absent from the public gallery listing; admin cover thumbnails stay behind admin authentication. If no cover is selected, the card uses a neutral theme-based placeholder. Removing a cover photo from the gallery also clears its selection.

## Import and publication sequence

The mounted browser import screen follows this server sequence; any compatible API client must follow it too:

1. Create `POST /api/v1/admin/galleries/:eventId/imports` with a client-generated import ID, total photo count, and the gallery's **Offer original files** choice. That choice remains attached to the import after a browser restart.
2. Declare at most 50 photo records in each `POST /api/v1/admin/imports/:importId/photos` chunk.
3. Upload all five derived variants per photo: `thumb`, `small`, `medium`, `large`, and `download`. If the import kept originals, also upload the unchanged JPEG, PNG, or WebP source (up to 100 MB per file).
4. Finalize each photo only after all required variants and any selected original exist.
5. Review `GET /api/v1/admin/galleries/:eventId/publication`, then publish with `POST /api/v1/admin/galleries/:eventId/publish` and `visibility` of `published` or `unlisted`.

**Gallery availability** is the reversible visibility control, not an upload button. Publishing requires every photo derivative to be ready, changes those ready photo rows to `published`, and makes the gallery public or unlisted in the same D1 batch. **Offline** immediately blocks gallery metadata, media, protected access, and face search while retaining D1, R2, and Vectorize data for republication. Taking a protected gallery offline also increments its access version so existing guest grants cannot become valid again after republication. Optional facial indexing can finish later without delaying publication.

The server enforces `MAX_PHOTOS_PER_EVENT`, `MAX_STORAGE_BYTES`, MIME/magic-byte agreement, byte size, dimensions, and SHA-256 checksum. An import is idempotent only when the same natural IDs and chunk contents are replayed; conflicting IDs return a conflict rather than being silently reused.

## Visitor downloads

**Allow downloads** is a per-gallery setting and can be changed later. A normal import always produces a prepared JPEG download copy, at most 3840 pixels wide without upscaling. If **Offer original files** was on when that photo was imported, the unchanged source is also stored privately. While both settings are on, visitors download that original in its actual JPEG, PNG, or WebP format. Otherwise they receive the prepared copy; for an older photo without that copy, the Worker serves its largest available display version. Enabling originals later does not recreate them for older photos.

Disabling downloads or original delivery stops serving originals and prevents new imports from retaining them. If originals from earlier imports remain, Gallery settings shows their count and storage size until they are removed. **Delete stored originals** opens a confirmation and queues background cleanup in Cloudflare; prepared photos and their downloads are kept. Finish an ongoing original-file import first, or use **Cancel unfinished imports** if you deliberately want to stop it. Cleanup begins after a short grace period for uploads already in progress. The warning disappears after cleanup finishes; it stays visible if cleanup needs another attempt. Files already saved by visitors cannot be recalled. Keep your own photo archive outside Cadrora.

In the public gallery, **Select photos to download** lets visitors choose individual photos or all currently visible downloadable photos. Shift-click selects a range, skipping photos without download variants; Ctrl+A / ⌘A selects all visible downloadable photos while selection mode is active. Unavailable photos are visibly marked with an information icon; clicking one or the information button beside **Select visible downloadable photos** explains the available/visible count and why it can differ. One selected photo downloads directly. For two or more, browsers supporting directory selection stream separate images directly into the visitor's chosen folder. Select or create a normal folder first: Chromium may refuse direct write access to special folders such as the top-level Downloads or Documents folder with a "contains system files" warning. Cadrora no longer steers the picker to Downloads; if the picker declines access, it explains the issue and leaves the ZIP action available. A ZIP is also the fallback on browsers without directory selection; it is generated on the visitor's device and capped at 100 photos and 250 MB per batch. The Worker only streams individually authorized media, never constructs an archive. If one request fails, the selection remains available for retry; the selected folder may contain already completed files. Existing filenames are preserved by adding a numeric suffix on repeat saves. The selection panel presents only actions and progress; detailed browser and keyboard instructions remain in this guide.

The official `CADRORA_SEED_DEMO=true` showcase enables downloads for the AI gallery and seeds full prepared `download` variants for its first five generated photos. Its other photos use their best available display version as the fallback. Re-running the opt-in demo seed repairs the five private R2 objects and D1 rows idempotently. A real site must not enable demo seeding.

Publication requires at least one photo and no visible photo outside `variants_ready` or `published`. Facial indexing is optional and does not block a gallery.

## Delete and purge behavior

Deleting a photo immediately changes D1 state to `deleting`, so media lookup returns 404 before provider cleanup finishes. It enqueues a `delete_photo_media` maintenance job. Face purging similarly enqueues `purge_event_faces`.

Deleting a whole gallery is intentionally separate from **Offline** and cannot be undone. In gallery settings, choose **Delete gallery**, then type the current title exactly. The Worker repeats that case-sensitive confirmation check, sets the gallery offline and deletion-pending, revokes protected grants, cancels open imports, and freezes photo writes. It queues a `delete_gallery` job with a five-minute quiescence window. The job removes only that gallery's D1-derived R2 media keys and Vectorize IDs, deletes its dependent D1 records, and deletes the gallery last. It never removes shared face-model files.

The Worker defines a 15-minute Cron Trigger that enqueues expired face purges and runs maintenance. It has no administrative maintenance-job screen. Confirm the trigger has actually executed and the relevant job reached `completed` before claiming physical R2/Vectorize deletion is complete. Gallery deletion keeps retrying provider failures with bounded exponential delay and remains inaccessible throughout.

## Operator habits

- Keep admin credentials, session cookies, Turnstile secrets, and event passwords out of tickets and screenshots.
- Check the exact hostname when testing protection; custom, preview, and `workers.dev` must behave alike.
- Review `GET /api/v1/admin/usage` as an application snapshot, not a Cloudflare bill or quota guarantee.
- Preserve the static `/` and `/contact` public website while testing admin paths.
